# Myself IDE — правила работы агентов

## Границы проекта

Работать только с этим форком и его текущими наработками. Не менять оригинальный checkout VS Code, baseline-приложение или другие проекты пользователя. Читать и изменять уже имеющийся код внутри нашего форка разрешено. Не выполнять fetch/pull/merge/rebase из `upstream`, не обновлять базу Microsoft и не отправлять туда изменения. Для GitHub использовать только `origin`, предварительно проверив его URL.

Контекст для нового чата: [docs/project-handoff.md](docs/project-handoff.md). Цель и полный реестр решений: [docs/project-plan.md](docs/project-plan.md). Состояние реализации: [docs/myself-ide.md](docs/myself-ide.md). План и распределение работы: [docs/development-plan.md](docs/development-plan.md). Задания: [docs/agent-prompts/README.md](docs/agent-prompts/README.md). Контракт PDF: [docs/document-export-contract.md](docs/document-export-contract.md).

## Параллельная работа

- Один агент — одно задание из плана, отдельная ветка и отдельный рабочий каталог. Не переключать ветку в каталоге другого работающего агента. Предпочитать уже выделенный checkout; для нового worktree использовать штатный инструмент среды, если он доступен.
- Не писать вне своего списка файлов. Нужное изменение в общей области записать в собственный отчёт для интегратора. Не откатывать и не перезаписывать чужие изменения.
- Владельцем общих файлов, зависимостей, сборки, main и релизов является интегратор. Остальные агенты не меняют `product.json`, корневые package/lockfiles, build pipeline, общие entrypoints, AGENTS, план и контракт.
- Не делить `node_modules`, `out`, `out-vscode`, `.build` между рабочими каталогами. Не запускать параллельно полные typecheck/bundle/package. Они выполняются на общем пакете изменений перед релизом по правилам ниже.
- База запуска — актуальный `main`, включающий седьмую итерацию (`99373603913f162e9d1256cc621949b8bdef03c0`) и правило пакетных сборок (`01293638a16`) либо более новые инструкции. Перед стартом убедиться, что он является предком HEAD. Не начинать от старой phase-ветки или оригинального VS Code.
- Статус своего задания вести только в `docs/agent-reports/<task-id>.md`: база, область правок, готовность, тесты, ограничения, необходимые подключения интегратором и итоговые коммиты. До запуска агента назначить ему task-id; не запускать двух владельцев одного задания.
- Публиковать task-ветку/PR можно в `origin`; `main` обновляет только интегратор после проверок. Готовая работа должна попасть в main, а не остаться только в phase/task-ветках. Не удалять чужие ветки и не переписывать публичную историю.

## Требования продукта

- Не возвращать встроенные AI/Copilot/Sessions, телеметрию, crash upload, рекомендации и автообновления расширений.
- Сохранять Git/GitHub authentication code, SSH, терминал, Tasks, настройки, extension host/API, ручной VSIX и обновление, подсказки методов, ручные форматтеры, Markdown/Mermaid/math и большие файлы.
- Публичная поставка без предустановленных языковых расширений. Персональный языковой набор пользователя — отдельная установка, не зависимость сборки.
- Локальная история сохраняется. Отсутствие аналитики не означает запрет необходимых Git/SSH/catalog/security запросов. Не объявлять полное удаление AI, пока общие реализации ещё присутствуют.
- Документы: обычный текст и PDF одной кнопкой, без обязательного TeX, сервера, учётной записи или облачной обработки. Для PDF использовать имеющийся Electron; не добавлять отдельный Chromium/Puppeteer/TeX в поставку без обсуждения реальной необходимости.
- Ранее удалённая Command Palette не должна быть единственным способом вызвать новую функцию: нужны видимые кнопки/меню.

## Сборки пакетами, а не после каждой правки

- По умолчанию накапливать несколько законченных изменений/задач в один релизный пакет. Отдельная правка, коммит, завершение задания агента или очередное сообщение «дальше» не являются поводом для полной сборки, упаковки или нового релиза.
- Во время разработки выполнять только необходимые целевые lint/tests, инкрементальную транспиляцию и узкие проверки типов. Переиспользовать успешные результаты, пока соответствующий код и зависимости не менялись. Полный typecheck общих контрактов/DI объединять на интеграционном дереве для всего пакета.
- Интегратор записывает состав пакета в своём отчёте, собирает готовые изменения агентов, проверяет их совместимость и запускает один общий цикл: необходимые интеграционные проверки → production bundle/package → native smoke ключевых сценариев и новых функций → подпись/privacy audit → публикация релиза. Сначала завершить планируемые правки пакета, затем запускать этот цикл.
- Повторять только затронутые проверки/этапы после реального исправления ошибки или изменения входных данных сборки. Не повторять успешный цикл ради коммита, merge, оформления отчёта или смены чата. Документация, AGENTS, планы и промпты не требуют сборки, перепаковки ради нового SHA или бинарного релиза; релизный тег должен указывать на фактически собранный исходный коммит.
- Досрочная полная сборка допустима, если пользователь явно запросил готовую сборку сейчас либо конкретный дефект можно воспроизвести/проверить только в собранном приложении. В отчёте указать причину; не превращать это исключение в проверку каждой правки.
- Готовые изменения можно коммитить и передавать интегратору после целевых проверок, честно отмечая, что общая релизная проверка ещё впереди. Перед выпуском пакета обязательные проверки не пропускать; сбой блокирует публикацию, а не отменяет правило объединять изменения.

## Проверки и Git

Соблюдать действующие технические правила [.github/copilot-instructions.md](.github/copilot-instructions.md) и [.github/instructions/committing.instructions.md](.github/instructions/committing.instructions.md), где они совместимы с указаниями пользователя и этим планом. Для зависимостей — pnpm с версиями из репозитория; не выполнять массовое обновление зависимостей.

Начинать с `git status` и чтения своего задания. Проверки выбирать по изменению: целевой lint, содержательные тесты, при необходимости транспиляция; полный client typecheck — для изменений общих контрактов/DI и интеграции. Не объявлять тест пройденным, если он не запускался. Одно скрытие кнопки не считать удалением реализации.

Коммиты использовать с GitHub noreply. Не отключать hooks или пользовательскую подпись. Не публиковать локальные абсолютные пути, личный email, токены, пользовательские настройки и приватные отчёты. Перед релизом обязательны существующий build-path guard, проверка ASAR после подписи и native smoke; инструкция подписи — в docs/myself-ide.md. Не помещать пользовательские данные в тестовые фикстуры.

## Готовность задания

Изменения ограничены согласованной областью; ручные сценарии сохранены; релевантные проверки выполнены; собственный отчёт заполнен. Агент передаёт интегратору коммит/ветку, зависимости и точные точки подключения. Заглушки, TODO и непроверенные предположения обозначать явно. При конфликте областей остановить только зависимую правку, продолжая независимую часть задания.
