# Проверить мою установку

Задание `installation-diagnostics`. База `445e1988539`, ветка `codex/installation-diagnostics`. Область: `src/vs/workbench/contrib/myselfDiagnostics/{common,browser,test}/` и этот отчёт.

## Архитектурное предложение

Штатное действие `Action2` в меню Help открывает информационный диалог со снимком текущего окна. В диалоге отображаются версия работающего продукта из `IProductService`, имя `IUserDataProfileService.currentProfile` и статусы четырёх пакетов из [отчёта C/Python](debt-cleanup-c-python.md): `llvm-vs-code-extensions.vscode-clangd`, `vscode.cpp`, `detachhead.basedpyright`, `vscode.python`. Пакеты подсветки помечаются отдельно. Статус запуска показывается только для пакетов языковых серверов.

Установку сверяем с локальным установленным набором рабочего окна. Рабочий кэш `IExtensionsWorkbenchService.whenInitialized/installed` предпочтителен: `queryLocal` может запрашивать контрольный манифест и поглощает ошибки пакетного поиска, а самостоятельный вызов сканера может инициализировать отсутствующий реестр профиля. Отсутствие в кэше формулируется как «Нет в локальном списке». Для включения используется `IWorkbenchExtensionEnablementService` с текущими правилами Workspace Trust. Для активации используются `IExtensionService.extensions` и `getExtensionsStatus()`: успешное завершение фиксируют `activationTimes` соответствующего локального экземпляра. Незарегистрированный экземпляр и начатая без подтверждения активация имеют неопределённое состояние. Ошибки чтения заменяются короткими локализованными статусами, без сообщений исключений.

Профиль и данные записи должны соответствовать одному снимку. Смена профиля в процессе сбора делает снимок устаревшим. На время обновления инвентаря после смены профиля следует показать недоступность результатов, чтобы кэш прошлого профиля не получил имя нового. Состояния установки, включения, активации и запуска LSP независимы. Для LSP всегда отображается «Не проверено», поскольку существующий контракт расширений сообщает только о самом расширении.

Публичных контрактов и регистраций сервисов не требуется. Просмотр `IConfigurationService` подтвердил возможность чтения настроек по ключам и resource overrides. В первом экране не читаем настройки расширений, поскольку их значения зависят от ресурса и могут содержать локальные пути, а существующий общий контракт не подтверждает выбранное окружение Python или доступность сервера. Диагностика не активирует расширения, не запускает процессы и команды, не обращается к каталогу, файлам проекта, окружению или секретам, не экспортирует данные и не меняет настройки.

## Реализация

Первоначальный код и тесты зафиксированы в `bf44fa38611071833060f36fbec91235a94ae32f`. Исправление смены профиля при старте и регрессионные тесты зафиксированы в `a733dadf83cc0df2ffb0bef2fb0614cfad2274df`. Меню видимо в локальном desktop-окне после восстановления workbench и окончания регистрации расширений. Применены штатный диалог и локализация. Английская строка по умолчанию — **Help → Check My Installation**. Русские строки для языкового пакета остаются отдельной локализационной работой.

`IExtensionsWorkbenchService` уже создаётся штатной `ExtensionsContributions` на `LifecyclePhase.Restored` в [extensions.contribution.ts](../../src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts). Её импорт из common entrypoint должен предшествовать импорту диагностики в desktop entrypoint. На `WorkbenchPhase.BlockStartup` наблюдатель подписывается только на уже созданный `IUserDataProfileService`. На `AfterRestored` сборщик подписывается на сброс существующего кэша и наблюдает готовность `whenInitialized`. Данные `installed` читаются по команде. Повторного вызова инициализации, инвентаризации или загрузки манифеста нет. Локальный кэш может молча пропустить пакет при недоступной инвентаризации, поэтому «Нет в локальном списке» описывает наблюдение кэша. Удалённые и workspace-scoped пакеты исключаются.

Во время смены профиля сборщик отбрасывает начатый снимок, в том числе при переходе A → B → A. После смены профиля с другим реестром расширений требуется сигнал обновления кэша и завершение перехода профиля. При наложении двух обновлений сигнал кэша не позволяет восстановить принадлежность списка. В этом случае диалог предлагает открыть окно заново. Сам сигнал `onReset` и переименование профиля с тем же `extensionsResource` не снимают отметку наложения. Снять её может последующий переход с другим `extensionsResource`, начавшийся без outstanding resets, после подтверждённого завершения этого перехода и сброса. Если сброс произошёл до подписки сборщика или до готовности исходного кэша, принадлежность списка остаётся неподтверждённой. Повторное открытие окна начинает диагностику с нового кэша профиля. Для подтверждения активации совпадают ID без учёта регистра, версия и URI зарегистрированного экземпляра. В диалог попадает только статус, без URI и содержимого исключений.

Штатный `CommandService` вызывает расширения, явно подписанные на событие соответствующей команды. Диагностика не добавляет такую подписку. Регистрация действия после `whenInstalledExtensionsRegistered()` исключает раннюю запись отложенного события активации при обычном запуске. Произвольное стороннее расширение может самостоятельно объявить подписку на этот ID. Общий механизм расширений и Workspace Trust сохраняются.

## Проверка гонки при старте

В [desktop.main.ts](../../src/vs/workbench/electron-browser/desktop.main.ts) начальный профиль устанавливается до создания workbench. Реестр contributions создаёт `BlockStartup` синхронно при старте, до восстановления окна, а `AfterRestored` выполняется через idle callbacks. Смена профиля может попасть между этими фазами. [UserDataProfileService](../../src/vs/workbench/services/userDataProfile/common/userDataProfileService.ts) присваивает новый профиль до рассылки события и ожидания присоединённых операций. [ProfileAwareExtensionManagementChannelClient](../../src/vs/workbench/services/extensionManagement/common/extensionManagementChannelClient.ts) присоединяет смену профиля расширений, но её уведомление лишь запускает асинхронный `Extensions.reset()`. `whenSettled` профиля не ждёт заполнения workbench-кэша. Событие `onReset` не содержит профиль или номер перехода и не воспроизводится для новых слушателей. Сброс до готовности кэша также не доказывает, что штатный запрос при старте не перезапишет его.

Новый тест с настоящим `UserDataProfileService` удерживал A → B через присоединённый promise. При создании сборщика после присваивания B исходный код вернул B / `available` / `installed` для clangd из A. На исходной реализации прогон сборщика дал 6 успешных тестов и 1 падение. После исправления сборщик возвращает `unavailable` до завершения перехода и наблюдаемого сброса после готовности кэша. Отдельные сценарии покрывают сброс до подписки и перезапись сброса поздним ответом при старте.

- Повтор описанной команды `run-tests.mjs` для двух suite — 13 из 13.
- Повтор `check-types.mjs` для пяти файлов — 0 диагностик.
- `node "$CHECK_DIR/smoke-profile-lifecycle.mjs"` — проверка с реестром contributions, DI и `CommandService`. До `Restored` сервис инвентаря не создан. Переход до `AfterRestored` замечен. Меню показывает профиль B без пакетов A, а после подтверждённого сброса показывает текущий список.
- `git diff --cached --check` — успешно. Для этого SHA пакетный ESLint и нативный запуск остались на интеграции. QA через тимлида может повторить регрессионный сценарий на коммите с исправлением.

## Подключение и приёмка

В `src/vs/workbench/workbench.desktop.main.ts` после существующих импортов **Extensions Management** интегратор добавляет:

```ts
import './contrib/myselfDiagnostics/browser/installationDiagnostics.contribution.js';
```

В пакетном checkout после целевой транспиляции запустить `VSCODE_SKIP_PRELAUNCH=1 scripts/test.sh --runGlob 'vs/workbench/contrib/myselfDiagnostics/test/**/*.test.js'`. Перед выпуском проверить нативное меню и диалог в изолированных профилях, переключение профиля, отключённое расширение, Restricted Mode и отсутствие сетевого и дочернего процесса при открытии. Архитектурные замечания об источнике и фазе создания учтены. Независимая проверка итогового SHA безопасником и QA остаётся в пакетной приёмке.
