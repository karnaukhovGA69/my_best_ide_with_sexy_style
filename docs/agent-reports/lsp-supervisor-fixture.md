# Владение процессом языкового сервера после выхода клиента

Задача `lsp-supervisor-fixture`, направление №18. База `18d423a85e6`, ветка `codex/lsp-supervisor-fixture`. Изменения содержатся в двух файлах `extensions/myself-language-servers/test/**` и этом отчёте.

## Проверенный сценарий

Тестовый harness запускает текущий доверенный Node по абсолютному пути. Координатор A подаёт тестовый Start, после чего harness запускает отдельный supervisor. Оба процесса — прямые дети теста. Supervisor владеет синтетическим сервером. Все управляющие команды имеют фиксированные роли. В окружение процессов не копируются переменные пользователя, shell выключен. Все тестовые установки находятся в собственном каталоге `mkdtemp` с приватными правами, в отдельном дереве `runnable-fixture-only`. Хранилище IDE и реальные архивы не используются.

1. Supervisor открывает постоянный файл блокировки конкретного UUID через существующий `tryAcquireLease`. Darwin `O_EXLOCK` удерживается открытым дескриптором. В тесте дескриптор специально дублируется в FD 3 сервера. Сервер сверяет устройство и inode, закрывает FD 3 и проверяет результат `EBADF`. Совпадение с inode supervisor и файла в каталоге проверяется до аварии клиента.
2. Harness завершает координатор A по его собственному `ChildProcess` и получает реальный выход `SIGKILL`. После этого сервер подтверждает жизнь ответом на новый случайный nonce. Второй клиент запускается отдельным процессом, получает **busy** от того же lease inode и оставляет тестовую установку на месте. Новый nonce подтверждает, что сервер всё ещё жив. Параллельная тестовая установка другого UUID удаляется.
3. Supervisor запрашивает остановку сервера и ждёт события `exit` своего дочернего процесса. Даже после этого сигнал **busy** сохраняется, пока тест удерживает lease для проверки порядка. Затем supervisor закрывает дескриптор, подтверждает **released** и завершается. Повторный вызов второго клиента захватывает тот же inode и удаляет только нужный тестовый каталог. Файл lease сохраняет inode, а соседний синтетический каталог `managed` остаётся доступным.
4. Дедлайны и блоки `finally` обслуживают собственные `ChildProcess` test harness и supervisor. В успешных и проверенном отрицательном прогоне временные каталоги удалены. При ошибке подтверждения выхода supervisor harness останавливает только свой процесс и сохраняет тестовый каталог для диагностики. Поиск или завершение процессов по сохранённым PID отсутствуют.

## Проверки

На macOS 26.6.2 ARM64, Node 26.8.2 прошёл обычный запуск и 6 из 6 повторов с запретом сети на уровне процесса. Контрольный прогон на временной копии с досрочным закрытием lease упал на ожидании **busy**, поскольку второй клиент смог удалить синтетический пакет. Целевая строгая проверка двух файлов TypeScript 6.0.3 и целевой ESLint с `--no-ignore` прошли. Никакого IDE build, GUI или установки. Интеграционный прогон выявил, что дочерние процессы Electron требуют явный `ELECTRON_RUN_AS_NODE`. После поправки тест прошёл отдельно на Node 24.22.1 из установленного приложения и Node 26.8.2 под запретом сети.

Из корня репозитория:

```sh
node --experimental-strip-types --test extensions/myself-language-servers/test/supervisor.test.cts
/usr/bin/sandbox-exec -p '(version 1)(allow default)(deny network*)' "$(command -v node)" --experimental-strip-types --test extensions/myself-language-servers/test/supervisor.test.cts
```

На другой платформе тест пропускается. `package-vsix.mts` складывает в пакет только скомпилированный entrypoint, manifest и файлы лицензий. Тест не подключается из runtime и не добавляет команд, зависимостей или файлов в VSIX.

## Граница будущего Start

Проверено владение lease после завершения отдельного клиента. Родителем supervisor в стенде служит harness. Для эксплуатации нужно отдельно проверить запуск фиксированного подписанного runtime из Extension Host, жизнь supervisor после потери родителя и реакцию на завершение самого supervisor. В подлинном запуске не передавать lease FD серверу. Darwin-флаги этого теста нельзя переносить на другие платформы без проверки.

Если supervisor аварийно завершится, ядро может освободить lease при ещё живом процессе. До реализации этой обработки нужен отдельный достоверный сигнал состояния, который не разрешит Remove при неизвестном исходе. Выход прямого потомка также не подтверждает выход его возможных дочерних процессов. Поведение дерева процессов и граница ОС требуют отдельной проверки. Тест не подтверждает sandbox или доверие к загруженному исполняемому файлу.

Будущий runnable store должен иметь самостоятельный корень вне `<globalStorage>/managed` с собственным Remove. Старый импортёр адресует только legacy-корень, и установка исполняемых пакетов в этот корень не подходит для новой модели владения. В этом изменении обе структуры смоделированы внутри временной папки, `PackageStore` и старый Remove не менялись. Нативное подключение Start остаётся открытым.
