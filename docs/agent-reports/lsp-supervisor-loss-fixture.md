# Запрет удаления после аварии supervisor

Задача `lsp-supervisor-loss-fixture`, направление №18. База `29b97518fb8afe130a11e20ac5786920b010863c`, проверенный код `60824cfda32561ffee43f38a1013caf556293259` в ветке `codex/lsp-supervisor-loss-fixture`. Область правок — `extensions/myself-language-servers/test/**` и этот отчёт.

## Сценарий

Стенд создаёт синтетический пакет в приватном временном каталоге. Файл состояния находится рядом с постоянным Darwin lease конкретного UUID, вне удаляемого каталога пакета. Интерпретатор запускает только штатные тестовые сценарии через IPC. Хранилище владельца, архивы и runtime VSIX в проверке не участвуют.

1. Supervisor захватывает kernel lease, эксклюзивно создаёт маркер `starting` с новым поколением и полностью записывает его до подтверждения старта. При наличии старого маркера он возвращает **start-refused**, сохраняя данные. Standalone Remove на этом этапе подтверждает, что kernel lease занят.
2. После подтверждения harness запускает синтетический сервер и один раз связывает его `ChildProcess` с поколением маркера. Статусы `running` и `unknown` записываются supervisor под тем же lease. Маркер ограничен 512 байтами. Проверяются обычный тип файла, владелец, режим, число ссылок и совпадение inode, чтение идёт без следования ссылкам.
3. Harness посылает SIGKILL своему supervisor и ждёт выхода. Сервер отвечает на два свежих nonce, до и после попытки удаления. Второй отдельный Remove-клиент захватывает уже свободный lease на **том же inode**, читает маркер и возвращает **ownership-unconfirmed** для `starting`, `running` и `unknown`. Состояние и содержимое пакета сохраняются.
4. До наблюдаемого выхода связанного процесса harness не может снять маркер. После остановки по IPC он ждёт события `ChildProcess.exit` с `code=0` и без сигнала. Remove продолжает отказывать до очистки маркера. Harness под вновь захваченным lease сравнивает текущее поколение со своим подтверждением выхода и только после совпадения снимает маркер. Remove затем удаляет синтетический пакет, оставляя inode lease на месте.
5. Подтверждение старого поколения после реального выхода процесса не снимает новый маркер. Неполный JSON, запись больше лимита и висячая ссылка дают отказ. В стенде только явный `ENOENT` означает отсутствие маркера при условии, что маркер записывается перед каждым запуском и снимается только после подтверждённого выхода.

Supervisor и синтетический сервер — отдельные прямые дети harness. SIGKILL, освобождение kernel lease, IPC, жизнь и выход процесса наблюдаются реально. Передача полномочий наблюдателя на harness моделируется. Фикстура заканчивает собственные процессы по сохранённым объектам `ChildProcess` и удаляет временный каталог после их выхода. Проверка отмены запрещает запуск нового процесса, когда тест уже завершает работу по таймауту. Поиска процессов по PID и автоматического восстановления владения в стенде нет.

## Результаты

На macOS 26.6.2 ARM64 с Node 26.8.2 прошли 6 из 6 тестов, пять новых сценариев и предыдущий сценарий падения координатора. Повторено три раза под системным запретом сети, каждый раз 6 из 6. Целевые строгие проверки TypeScript 6.0.3 и ESLint с `--no-ignore` прошли.

Контрольные изменения выполнялись на отдельных временных копиях тестов под запретом сети. Отключение проверки маркера в Remove дало фактическое **removed** вместо ожидаемого **ownership-unconfirmed** при ещё живом сервере. Отключение сравнения поколения позволило старому подтверждению снять новый маркер, тест упал на ожидаемом отказе. В рабочей ветке оба условия сохранены. Независимое ревью подтвердило порядок запуска, владение lease, привязку поколения к процессу и защиту удаления. По замечанию ревью добавлена проверка отмены перед каждым запуском дочернего процесса.

Из корня репозитория:

```sh
/usr/bin/sandbox-exec -p '(version 1)(allow default)(deny network*)' "$(command -v node)" --experimental-strip-types --test \
  extensions/myself-language-servers/test/supervisor.test.cts \
  extensions/myself-language-servers/test/supervisor-loss.test.cts
```

В этой задаче использован установленный Node, режим packaged Electron не запускался. Проверка относится к аварии процесса. Для реализации в IDE нужно доказать, кто достоверно наблюдает выход после потери supervisor. Стенд не подтверждает восстановление после отключения питания, защищённость от другого процесса с тем же UID, управление потомками сервера или запуск загруженного LSP. Старт приложения, сборка и установка пакета не выполнялись.
