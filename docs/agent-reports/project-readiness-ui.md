## Поведение

Действие `myself.project.checkReadiness` добавлено в меню Terminal рядом с Tasks и в заголовок Explorer. Оно доступно в Restricted Mode. По нажатию штатный диалог показывает отдельный блок для каждой папки, состояние шести маркеров C и Python и вид настройки интерпретатора с её источником. Для одинаковых имён локальных корней в заголовке есть путь. Пустое окно получает подсказку об открытии папки. Отсутствие маркера отдельно от непроверенного состояния. Диалог показывает наблюдения о папке, а работоспособность инструментов, интерпретатора и языкового сервера остаётся непроверенной.

## Трасса и границы сбора

- При запуске действия контроллер снимает состояние корней и ждёт инициализации Workspace Trust. Restricted Mode даёт информационный результат без обращения к файловому провайдеру и без чтения настройки Python.
- Для доверенного workspace допускаются только абсолютные локальные `file:` URI с пустыми authority, query и fragment. Сборщик берёт уже зарегистрированный `IFileService.getProvider(Schemas.file)` и вызывает `provider.stat(joinPath(root, marker))`. В desktop workbench этот провайдер регистрируется в `electron-browser/desktop.main.ts`. Запросы ограничены четырьмя одновременно по всему workspace. Перед каждой новой пробой перепроверяются доверие и регистрация провайдера.
- `FileService.stat`, `exists` и `canHandleResource` проходят через `activateProvider` и могут запустить обработчики активации. Прямой `getProvider` читает реестр. Сборщик использует только `stat` для фиксированных маркеров. Бит `FileType.SymbolicLink` имеет приоритет над типом файла или каталога, включая оборванную ссылку. Явный `FileNotFound` даёт «отсутствует», остальные ошибки провайдера дают «не проверено». Ошибки и цели ссылок не отображаются.
- Native `DiskFileSystemProvider.stat` через `SymlinkSupport.stat` может обратиться к метаданным цели символической ссылки. Маркировка ссылки в результате не является гарантией no-follow. Локальный синтаксис URI также не определяет тип монтирования ОС. Это ограничение касается явно запущенной проверки доверенного проекта. У самого вклада нет сетевых запросов, обращения к терминалу, выполнения задач, чтения содержимого файлов или записи.
- `IConfigurationService.inspect` вызывается только для `python.defaultInterpreterPath` с `resource: root`. Явный слой сверяется с эффективным значением. Ошибка чтения даёт «не проверено» для настройки этого корня, сохраняя его маркеры и результаты других папок. Относительная запись связывается с папкой только в Folder Settings или в настройках workspace, открытого как одна папка. `${workspaceFolder}/` распознаётся как форма настройки в этих областях. Вычисление переменных, поиск по PATH, выбор `.venv` и stat пути интерпретатора отсутствуют. Сырое значение и ошибка не передаются в диалог.
- Изменение корней, состояния workspace, доверия, релевантной настройки или регистрации `file:` и закрытие workbench отменяют показ. После асинхронного этапа контроллер сверяет корни, состояние и доверие повторно. Пока запрос выполняется или диалог открыт, повторное нажатие не запускает новый сбор. Уже начатый `stat` остаётся в провайдере до завершения.

## Подключение интегратором

В `src/vs/workbench/workbench.desktop.main.ts` рядом с `myselfProjectActions` добавить desktop-импорт:

```ts
import './contrib/myselfProjectReadiness/browser/projectReadiness.contribution.js';
```

В секцию workbench файла `build/lib/i18n.resources.json` добавить ресурс `vs/workbench/contrib/myselfProjectReadiness` с проектом `vscode-workbench`. Заголовок действия — ключ `checkProject`, исходная строка «Check Project», перевод «Проверить проект». Вклад регистрируется на `WorkbenchPhase.AfterRestored` и использует существующие сервисы desktop workbench.

Дополнительный тест подтверждает сохранение результатов при сбое `inspect`.
- TypeScript Compiler API с параметрами `src/tsconfig.json` дал 0 синтаксических и семантических диагностик по четырём новым TypeScript-файлам. После исправления повторная проверка двух затронутых файлов также дала 0 диагностик. Использованы объявления из `src/typings` и типы Node и Mocha.
- Стандартный `build/eslint.ts` дал два предупреждения `local/code-translation-remind` об ожидаемой i18n-регистрации и возвращает ненулевой статус из-за них. Прямой ESLint по тем же четырём файлам с отключением только этого правила и `--max-warnings 0` прошёл. После исправления штатный ESLint двух затронутых файлов прошёл без предупреждений. `git diff --cached --check` прошёл.
- Инструменты взяты из локального кэша в одном worktree. Проверки пройдены без открытия окон. Полный typecheck, упаковка и работа реального диалога проверяются в интеграционном пакете.

Целевая команда тестов с esbuild и Mocha из локального набора зависимостей.

```sh
node_modules/.bin/esbuild src/vs/workbench/contrib/myselfProjectReadiness/test/{browser,common}/projectReadiness.test.ts \
  --bundle --platform=node --format=cjs --target=node24 \
  --outbase=src/vs/workbench/contrib/myselfProjectReadiness/test \
  --out-extension:.js=.cjs --outdir="$check_dir" --tsconfig=src/tsconfig.json
node node_modules/mocha/bin/mocha.js --ui=tdd "$check_dir"/{browser,common}/projectReadiness.test.cjs
```
