# Project readiness для C и Python

Первый этап реализован в ветке `codex/project-readiness` от локального `main` (`445e1988539`). Коммит модели и тестов — `7ac4b09e3e64967aa75287e762a3d1184dafcd8c`. Независимый QA модели завершён. Архитектурная сверка остаётся этапом интеграции.

## Контракт модели

`evaluateProjectReadiness(snapshot)` принимает состояние Workspace Trust и массив снимков папок. Снимок идентифицирует папку её workspace URI и содержит наблюдения о шести фиксированных записях в корне. Для `.venv` ожидается каталог. Для `pyproject.toml`, `requirements.txt`, `CMakeLists.txt`, `Makefile` и `compile_commands.json` ожидаются файлы. Отсутствие записи после проверки, отсутствие сведений, неподходящий тип и непроверенная символическая ссылка дают отдельные результаты.

Снимок интерпретатора описывает явную настройку для ресурса и её источник (`user`, `workspace`, `workspace-folder`, `unknown`). Варианты — настройка отсутствует, цель не определена, абсолютная цель или цель с явной привязкой к папке. Для двух последних вариантов передаётся отдельный факт наличия файла-кандидата. Если настройка указывает на каталог среды, факт наличия относится к файлу интерпретатора внутри неё. Пропущенный снимок означает, что настройку не проверили. Привязку относительной цели модель сверяет с полным URI соответствующей папки. Модель сохраняет указанную цель при наличии `.venv` и оставляет разрешение строк настроек сборщику снимков.

Результат содержит наблюдения и темы для проверки по каждой папке. Маркеры CMake и Make могут сосуществовать. База компиляции оценивается отдельно. Отсутствие маркеров оставляет язык проекта неизвестным, а наличие файла-кандидата оставляет открытыми выбор интерпретатора, его работоспособность и наличие языкового сервера. Для виртуальных, удалённых и `file:` URI с authority возвращается причина отсутствия оценки. В Restricted Mode модель возвращает те же информационные наблюдения со статусом `blocked-by-workspace-trust`. Темы для проверки — коды для будущего UI, без команд и исполняемых действий.

## Подключение

Для сборщика снимков использовать `IWorkspaceContextService.getWorkspace().folders` и `IConfigurationService.inspect` с `resource: folder.uri`. Для явного `python.defaultInterpreterPath` сохранять источник и привязывать относительную цель только при известном корне. Не подставлять первый корень, не проверять PATH, не вычислять переменные окружения или команды. При отсутствии безопасно полученного факта о файле интерпретатора передавать `unknown`.

Перед обращением к `IFileService` фильтровать корни по URI и проверять, что путь вызова использует локальный провайдер без активации расширений. URI `file:` с пустым authority сам по себе не подтверждает локальность монтирования. Собирать метаданные только для фиксированных имён в локальном корне. `absent` означает подтверждённое отсутствие, ошибки доступа и неподтверждённый тип записи дают `unknown`, а непроверенные ссылки дают `unverified-link`. Факт `file` предназначен для обычного файла. Содержимое конфигов, рекурсивный обход и запуск процессов в этот этап не входят.

Встроенные `extensions/python` и `extensions/cpp` предоставляют языковые грамматики. Проверку инструментов и фактического выбора интерпретатора следует проектировать отдельно от оценки корневых маркеров. Если появятся Run, Build и Test, подключать их к штатному Tasks после явного действия пользователя с проверкой Workspace Trust. `AbstractTaskService.run()` уже проверяет доверие, а автоматический запуск Tasks идёт отдельным путём. Интегратору остаются сборщик снимков, UI и регистрация вклада в workbench.
