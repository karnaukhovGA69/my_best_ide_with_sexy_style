Дата: 24 ноября 2026. Задание: `vscodium-review`. Статус: исследование завершено, ниже предложения для следующих задач, не выполненные продуктовые функции. Собственные исходники проверены на `bd8d21823c8`; внешние материалы VSCodium — на `ca7f7b44b5e5c3faa663f6cdc043998f71936653`. Продукт независимо подготовил пользовательскую часть; тимлид сверил первоисточники, инженерные ограничения и существующий код. Продуктовая реализация, установка VSCodium и обновление базы VS Code не выполнялись.

## Что представляет собой VSCodium

[README](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/README.md) описывает репозиторий как скрипты сборки Code OSS с общественной конфигурацией. Его собственная ценность — поставка, настройка сервисов, сопровождаемые патчи и документация совместимости. Обычные файловые вкладки, Git/diff, терминал, профили и редактор происходят из общей основы Code OSS. Их не нужно переносить к нам заново; недавнее возвращение левой панели было изменением уже существующей настройки.

[prepare_vscode.sh](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/prepare_vscode.sh) отдельно применяет общие, insider, платформенные и пользовательские патчи. [Инструкция сборки](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/docs/howto-build.md#patch-update-process) описывает обновление не применившихся патчей. Это полезная практика сопровождения; переводить наш рабочий форк на другую базу или переписывать его ради этой схемы не предлагается.

## Приоритет 1: «Проверить мою установку»

Проблема подтверждена одним случаем разрыва профилей: английские расширения находились в smoke-профиле, а обычное окно использовало основной. Дополнительный недавний сценарий — проект Python требует своё окружение и пути импортов, а наличие глобального Python не объясняет пользователю готовность проекта. У VSCodium это освещают [миграция](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/docs/migration.md) и справка совместимости. Единый диагностический экран — наше предложение по мотивам этих уроков, не существующая функция VSCodium.

Ожидаемое поведение: видимая команда Help «Проверить мою установку» показывает запущенную версию, активный профиль, состав/состояние выбранных расширений и конфигурацию C/Python текущего проекта. Различать «файл найден», «расширение включено/активировано» и «работа сервера проверена». Не выдавать наличие бинарника или ноль диагностик за доказательство работающего анализатора.

Ответственный за будущую реализацию: разработчик IDE. Предлагаемая область — отдельная workbench contribution с использованием существующих product, profile, extension, configuration и file services; без изменения настроек и без чтения `.env`/secret storage. Первое действие в задаче — архитектурная проверка доступных контрактов и небольшой ADR, затем реализация read-only экрана. Запуск интерпретатора или языкового сервера возможен только отдельным явным действием и с сохранением Workspace Trust.

Приёмка: в сценариях «другой профиль», «расширение отключено», «не найден сервер» и «проект использует другую .venv» экран сообщает конкретную причину; пользователь находит её за 30 секунд без терминала. Во время обычного открытия экрана нет сети и запуска процессов. Экспорт диагностического отчёта имеет просмотр состава, исключает секреты и не отправляет данные автоматически.

Зависимости: архитектурное ревью границ сервисов; security review перед добавлением запуска процессов или экспорта. Независимый проверяющий: QA/CI, отдельные интеграционные фикстуры и короткий native smoke. Сложность: средняя. Это первая задача, которую рекомендуем взять в реализацию.

## Приоритет 2: восстановление локального набора VSIX

Проблема: английский набор и C/Python устанавливались отдельными пакетами; повторная потребность восстанавливать весь набор пока гипотеза. VSCodium [рекомендует VSIX Manager](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/docs/extensions.md#vsix-manager), но это отдельное расширение. Его [группы и закреплённые версии](https://github.com/zokugun/vscode-vsix-manager/blob/21d34804225dd1530ddd7e3999bb71b004c1cbad/README.md#groups) и [файловый источник](https://github.com/zokugun/vscode-vsix-manager/blob/21d34804225dd1530ddd7e3999bb71b004c1cbad/src/sources/filesystem.ts) дают подходящий образец. Реальная совместимость всего VSIX Manager с нашей IDE не тестировалась.

Ожидаемое поведение: пользователь выбирает локальную папку VSIX и manifest с ID, версиями, платформами и SHA-256, видит недостающие/конфликтующие пакеты и устанавливает выбранное в текущий профиль. Использовать существующий сервис установки; не копировать папки расширений напрямую. Не добавлять URL sources, автоматическую синхронизацию или загрузку недостающих пакетов. Лицензии включённых пакетов проверяются отдельно; контрольная сумма не доказывает подлинность издателя.

Ответственный за будущую реализацию: разработчик расширений/extension management. Границы — локальный manifest, выбор файлов, установка и результаты по каждому пакету; existing settings transfer и secret storage не менять. До кодирования архитектор проверяет формат и profile contract, безопасностный специалист — пути, tampering, подписи, полномочия и активацию расширений. Нельзя строить расширение этой функции на непроверенном Remove из прежнего LSP ZIP importer.

Приёмка: английский набор из трёх локальных пакетов восстанавливается максимум за три пользовательских действия без сети; неправильная архитектура и hash mismatch отклоняются до установки; отсутствующие зависимости и частичный результат явно показаны; повторный импорт не создаёт дубли; отключение/удаление работают штатно. Первым тестом проверить выбор фактического текущего профиля.

Зависимости: стабильный manifest contract и существующая установка локального VSIX; задача 1 желательна для понятного статуса, но её экран не обязателен для реализации установщика. Независимый проверяющий: QA/CI, изолированные профили и GUI-проверка восстановления. Сложность: средняя.

## Приоритет 3: прослеживаемость собственных изменений и сборок

Проблема: политика поставки распределена между product, allowlist, runtime filters и многочисленными исходными изменениями. Нужен один проверяемый ответ, какие именно изменения и версии инструментов вошли в пакет. Аналоги: упорядоченное применение патчей VSCodium, [prepare_src.sh](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/prepare_src.sh) с исходными архивами/checksums и buildinfo для insider, [macOS CI](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/.github/workflows/ci-build-macos.yml) с явной матрицей и закреплёнными action SHAs. Наличие этих скриптов не доказывает побитовую воспроизводимость сборок.

Ожидаемое поведение: дополнить существующий релизный процесс manifest с source commit, базой Code OSS, toolchain, платформой и digest собственных правил поставки. Выделить список изменений по модулям и regression gates. Не превращать весь форк обратно в набор patch-файлов и не запускать обновление upstream. Локальные пути, личные идентификаторы и секреты в manifest не включать.

Ответственный: инженер CI/CD, с согласованием общих файлов у интегратора; область — существующие build/release tools, policy tests и один manifest. Сначала просмотреть сохранённые два уникальных коммита `agent/nerded-ci-preflight`: там уже подготовлена проверка для GitHub-hosted macOS ARM64, но новый hosted workflow не подтверждён запуском и не интегрирован. Не создавать второй параллельный pipeline вместо доведения этого задела.

Приёмка: manifest согласован с фактическим исходным коммитом и артефактом; намеренное несовпадение обнаруживается проверкой; существующий ASAR/privacy guard сохранён; новая политика или изменение в allowlist требует соответствующего regression gate. Полный build выполняется только в общем релизном пакете. Перед включением CI отдельно проверить доступность и архитектуру runner, permissions и происхождение артефактов.

Зависимости: ревью архитектора и специалиста по безопасности для изменения поставки; независимая проверка — другой QA-инженер на dry-run без публикации и интегратор, не автор pipeline. Сложность: средняя/высокая; начинать с manifest и имеющихся checks, а не переписывания build system.

## Что не переносим автоматически

- Централизованный [фильтр команд ask/off/on](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/patches/00-security-add-command-filter.patch) — реальная особенность, но не sandbox расширений или процессов. У нас уже есть Workspace Trust; изменение общего CommandService потребует отдельного архитектурного/security разбора. [Отсрочка установки свежих обновлений](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/patches/12-update-add-cooldown.patch) тоже рассмотрена: в текущей ручной local-only поставке приоритетнее уже согласованные проверки пакета и правило его замены.
- Фоновые обновления приложения/расширений, сетевые announcements и загрузку extension control list: они описаны в [телеметрии и онлайн-сервисах VSCodium](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/docs/telemetry.md), но противоречат нашему первому local-only пакету. Идея локального списка отозванных расширений требует отдельного дизайна обновления и не считается готовой защитой без актуальных данных.
- [Патч отключения проверки подписей](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/patches/00-extension-disable-signature-verification.patch): он явно присваивает verifySignature=false в gallery download path. Это не предлагаемый способ решить совместимость VSIX.
- Неограниченный [пользовательский product.json](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/patches/00-settings-user-product.patch), proposed API allowlists и remote client validation changes. Каждая такая граница требует отдельного обоснования; чужой product.json нельзя целиком подставить вместо нашего.
- Облако, аккаунты и remote-функции остаются отложенными. Portable mode и Sync Settings не заменяют наш локальный перенос настроек и не должны незаметно менять профиль владельца.
- Крупные [Copilot JSON](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/patches/52-ext-copilot-remove-it.json) и [source patch](https://github.com/VSCodium/vscodium/blob/ca7f7b44b5e5c3faa663f6cdc043998f71936653/patches/53-ext-copilot-remove-it.patch) полезны как будущий справочник для проверки оставшихся зависимостей, но не переносятся поверх наших уже выполненных удалений без анализа потребителей.
