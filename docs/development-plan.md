## Первая параллельная волна

| ID | Задание | Владелец файлов | Зависимости и результат |
| --- | --- | --- | --- |
| documents-ui | Обычный текст, оформление страницы, кнопка PDF | `extensions/myself-documents/**`, собственный отчёт | Работает по фиксированному контракту PDF с mock; итоговая интеграция зависит от pdf-export |
| pdf-export | Локальный PDF на имеющемся Electron | `src/vs/platform/documentExport/**`, `src/vs/workbench/contrib/documentExport/**`, собственный отчёт | Независим от UI, принимает DTO; подключения к существующим entrypoints передаёт интегратору |
| ai-terminal-cleanup | Оставшиеся терминальные AI-команды и инструменты | `src/vs/workbench/contrib/terminalContrib/chatAgentTools/**`; `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatTerminalToolProgressPart.ts`; собственный отчёт | Сохраняет обычные терминалы/Tasks; общие подключения согласует с интегратором |
| mcp-audit | Карта безопасного удаления MCP | Только `docs/agent-reports/mcp-audit.md` | Чтение нашего форка, без изменений runtime; следующий этап после review |
| integration | Сборка результатов, проверки, main, релиз | Общие файлы и точки подключения, AGENTS/план/контракт | Один владелец; не редактирует активные области других агентов |

Промпты для запуска находятся в `docs/agent-prompts/`. Агенты A/B/C могут писать код одновременно в разных рабочих каталогах, D делает аудит. Изменения накапливаются в релизные пакеты по разделу «Сборки пакетами» в AGENTS.md. Один коммит или готовность одного агента не запускают релиз автоматически. Интегратор фиксирует состав пакета в своём отчёте; до завершения пакета выполняются целевые проверки. Тяжёлую итоговую сборку выполняет только интегратор: одновременные полные сборки конкурируют за RAM/CPU и могут перезаписывать общий каталог приложения.

## PDF: пользовательский сценарий

Пользователь выбирает «Новый документ» или открывает текстовый файл как документ, пишет ответы `а)1`, `б)3` или эссе обычным текстом, выбирает шрифт/размер/интервал и нажимает видимую кнопку «Экспорт PDF». Первый экспорт открывает стандартный диалог сохранения; перезапись подтверждается штатным способом. TeX, установка движка и подключение к интернету не нужны.

Первый MVP: `.txt`, UTF-8, абзацы и переносы без потерь, Unicode/кириллица/английский, выделение и вставка, undo/redo, поиск средствами доступного редактора, сохранение через VS Code document API. Визуальная оболочка документа — опциональный custom text editor, не замена редактора кода. Набор текста не требует Markdown. Параметры страницы относятся к экспорту; не сохранять их в сам текст и не обещать перенос этих параметров между устройствами без отдельного формата.

PDF: A4, поля, основной шрифт из ограниченного набора, размер и межстрочный интервал, автоматические переносы страниц, выделяемый/копируемый текст. Не преобразовывать весь документ в изображение. Нужны случаи на одну и несколько страниц; длинные строки и ручные номера ответов не должны обрезаться.

За рамками первого MVP: полная замена Pages, DOCX, плавающие изображения, сложные таблицы, совместное редактирование, формы PDF, обязательная грамматическая/AI-проверка. Следующая версия может добавить форматированный документ и Markdown/Mermaid/math export после выбора модели хранения и проверки сохранения без потерь. Библиотека документации Go/других языков — отдельная функция чтения/каталога, не часть этого редактора.

## Порядок интеграции

1. Зафиксировать назначения task-id и отдельные checkout/worktree от нашего main. Не выполнять checkout веток в общем каталоге.
2. PDF backend и UI разрабатываются по неизменяемому контракту `document-export-contract.md`. Предложение изменения контракта передаётся интегратору; оба потребителя должны быть согласованы до объединения.
3. Сначала объединить backend с тестами, затем UI и его регистрацию в built-in allowlist/build. AI cleanup можно объединить независимо после проверки терминала. MCP audit не разрешает автоматически массовое удаление кода.
4. Интегратор просматривает diff и приватность, выполняет нужные lint/tests/typecheck на общем дереве. Не переносить артефакты out/node_modules из task-веток.
5. После объединения всех запланированных изменений пакета — один общий production bundle/package. Не собирать отдельный релиз после каждой задачи. Native smoke: запуск/сохранение редактора, completion, ручной formatter, Git, zsh/bash, shell Task с exit0, ручной VSIX install→update→uninstall; отсутствие удалённых AI-команд. На пустой языковой поставке Tasks должны продолжать работать.
6. PDF smoke: набрать/сохранить/переоткрыть текст; export/cancel/ошибка записи; русский и английский, несколько страниц. Проверить извлечение текста и визуальную раскладку страниц, отсутствие сети и второго браузерного runtime. Для создания/инспекции PDF использовать доступный PDF skill, если среда его предоставляет.
7. Packaging privacy guard; deep signing → ASAR refresh → outer signing без deep → verify; аудит ZIP. Объединить проверенные изменения в main обычным merge/fast-forward без force. При PR убедиться, что он действительно merged. Не отправлять PR в Microsoft.
8. Опубликовать prerelease для проверенного пакета изменений приложения, проверить релизный тег/исходный коммит и checksum asset. Документационные изменения не требуют нового бинарного релиза или перепаковки ради SHA; main может содержать более новые документы, чем исходный коммит релиза. Повторный цикл нужен только после изменений, влияющих на сборку/проверки, либо по обоснованному исключению из AGENTS.md. Перенести статус в план и обновить краткий отчёт продукта.

## Следующие волны

- По результатам mcp-audit: безопасное удаление MCP UI/runtime/providers, затем общий Chat, inline completions и оставшиеся AI зависимости, с сохранением обычного IntelliSense и API не-AI расширений.
- Собственный GitHub OAuth, каталог репозиториев в выбранной папке, ручной приватный backup настроек без токенов и фоновой синхронизации.
- Библиотека локальной документации Markdown/PDF с выбором языка/набора.
- Общий лимит локальных диагностических логов; сохранение пользовательской истории.
- Личный языковой набор отдельно от публичной сборки.
- Терминальный прототип: оценка Ghostty/другого движка, затем внешняя интеграция; штатный терминал и shell-плагины сохраняются.
- Новый бренд и настраиваемый визуальный стиль после фиксации базовых компонентов.

Для эссе и коротких учебных ответов LaTeX не является требованием. Он может пригодиться позже для сложных формул, ссылок и строгой научной вёрстки; возможность экспорта PDF не должна зависеть от его знания.
