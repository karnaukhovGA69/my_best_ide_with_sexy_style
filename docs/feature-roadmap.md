# Nerded Code: следующая разработка

Решение владельца от 27 ноября 2026: реализовать все 27 принятых направлений. **Локальные шаблоны проектов исключены.** Нумерация сохраняет исходный список. Реализация и проверка идут пакетами. Сводка текущих назначений и проверок — в [отчёте второй волны](agent-reports/development-wave-2.md).

Диагностика установки, меню многофайлового просмотра Git и команда «Проверить проект» для C/Python прошли целевые проверки. Проверка установленного приложения относится к общему пакету. Владелец отложил обсуждение переноса на Rust. Сохранённые измерения остаются материалом для будущей оценки.

## Три приоритета первой волны

### installation-diagnostics — проверить установку

Проблема: наличие пакета в другой папке профиля или выключенного расширения не объясняет пользователю, работает ли его языковой набор. Ожидаемое поведение: видимое действие в Help показывает версию, действующий профиль и независимые состояния installed/enabled/activated. Работа языкового сервера обозначается как непроверенная, пока нет надёжного источника результата.

Ответственный: разработчик 2. Область: новая contribution `src/vs/workbench/contrib/myselfDiagnostics/**` и собственный отчёт. Использовать существующие product/profile/extensions services; не добавлять общий DI-контракт. Общую регистрацию подключает тимлид. Первый срез не экспортирует отчёт, не запускает процессы, не активирует расширения, не обращается в gallery и не читает секреты или конфигурационные файлы проектов.

Приёмка: отсутствие, отключение и неактивированное состояние различаются; смена профиля во время асинхронного чтения не смешивает два профиля; ошибка чтения не превращается в «всё работает». Открытие не меняет настройки и не запускает сеть/процессы. Проверка: целевые модельные тесты, проверка сборщика данных и видимого меню; native smoke в общем пакете. Зависимость: архитектурное ревью существующих сервисов. Независимые проверяющие: архитектор, безопасник, QA.

Уточнение ревью: inventory берётся из существующего **локального** extension management server с явно захваченным `currentProfile.extensionsResource`; общий `queryLocal` может обходить другие servers и скрывать ошибки. Успешная активация требует наблюдаемого завершения, а не только начала. Вызов `whenInitialized` широкого workbench-сервиса не является необходимым условием этого экрана.

### project-readiness — объяснить конфигурацию проекта

Проблема: открытая папка Python или C выглядит как текстовые файлы, а пользователь не видит, что известно об окружении и чего не хватает. Первый срез — чистая модель по ограниченному снимку маркеров и настроек, без автоматического исправления окружения. Отдельные результаты для каждого корня, несколько языков и явное «не проверено» вместо общего ready=true.

Ответственный: разработчик 3. Область: `src/vs/workbench/contrib/myselfProjectReadiness/common/**`, `test/common/**` и собственный отчёт. Первый срез не содержит файлового collector, UI, записи настроек или запуска команд. Маркеры `.venv`, `pyproject.toml`, `requirements.txt`, `CMakeLists.txt`, `Makefile`, `compile_commands.json` — признаки, а не доказательство работоспособности инструмента. Значение интерпретатора сопровождается источником конфигурации, без исполнения и поиска по PATH.

Приёмка: пустой/C/Python/смешанный проект, несколько корней, относительный интерпретатор, неизвестный факт, неподдерживаемая URI scheme и symlink не дают ложной готовности или выбора первого корня. Недоверенный проект не порождает исполняемых действий. Проверка: независимые unit-сценарии модели. Будущий collector должен отвергать remote/custom URI до обращения к provider, проверять только фиксированные имена и не читать содержимое файлов. Зависимость: архитектурный контракт снимка; UI/collector идут отдельным последующим срезом. Независимые проверяющие: архитектор, безопасник, QA.

Уточнение ревью: `FileService.stat` и `canHandleResource` могут активировать provider, поэтому сама схема `file` ещё не доказывает отсутствие побочных эффектов. Будущий collector требует отдельного проверенного adapter для уже зарегистрированного локального provider, без lazy activation. Сетевые mounts не становятся локальным sandbox от фильтра URI. Текущий pure-model срез не обращается к FileService.

### project-task-actions — запуск, сборка и тесты

Проблема: штатные Tasks есть, но владельцу нужны удобные видимые действия для работы с проектом. Ожидаемое поведение: «Запуск», «Сборка», «Тесты» делегируют существующему Tasks, сохраняют штатный выбор в multi-root и обработку отмены. Собственного движка процессов и автоматически сгенерированных shell-команд нет.

Ответственный: прежний разработчик IDE. Область: новая `src/vs/workbench/contrib/myselfProjectActions/**` и собственный отчёт. Общую регистрацию подключает тимлид. Этот срез независим от модели readiness; будущие подсказки можно подключить после её приёмки. Использовать существующие services/actions, не менять общие Tasks-контракты и настройки владельца.

Приёмка: trusted проект вызывает нужный штатный путь; restricted workspace отклоняет и прямой вызов команды до resolver/provider/process; отмена и отсутствие настроенных задач не исполняют команды; multi-root не выбирается за пользователя. Открытие меню ничего не запускает. Проверка: целевые тесты trust guard/dispatch/cancel и штатного меню; native smoke в общем пакете. Зависимость: архитектурный и security review запуска кода. Независимые проверяющие: архитектор, безопасник, QA.

Согласованный минимальный путь: дождаться `workspaceTrustInitialized`, проверить `isWorkspaceTrusted`, вызвать один из трёх фиксированных штатных command IDs без аргументов. Run обозначает «Запустить задачу…», не запуск текущего файла. Штатные Tasks сохраняют свои повторные проверки доверия, разрешение задач и picker; собственный picker/runner не добавляется. Завершение `executeCommand` не обозначает успешную сборку или тест.

## Срезы интерфейса первой волны

**project-readiness-ui.** Модель уже в `main`. Разработчик 3 подключает видимое действие и локальный сбор метаданных в `myselfProjectReadiness/browser` и `test/browser`. Для каждого корня показываются найденные записи, доступные сведения о конфигурации и то, что не удалось проверить. По явному действию в доверенной локальной папке сборщик проверяет метаданные фиксированных имён через уже зарегистрированный provider. Символическая ссылка отображается как непроверенная. В Restricted Mode метаданные файлов остаются непроверенными. Приёмка включает несколько папок, Restricted Mode, ошибку доступа, неизвестный тип записи и смену проекта во время чтения. Архитектор и безопасник проверяют источник сведений, QA повторяет сценарии. Интегратор подключает команду и локализацию.

**explorer-git-diff.** Разработчик проектных действий добавляет вход из панели Files в существующий MultiDiff. Пользователь открывает нужную группу изменений и продолжает видеть файлы. Область работы — меню и локализация встроенного Git. Использовать штатные `git.viewChanges`, `git.viewStagedChanges` и `git.viewUntrackedChanges`. Для нескольких репозиториев сохраняется штатный выбор. В приёмку входят отмена, пустой список, несколько репозиториев и отключённый Git. QA и интегратор независимо проверяют исходники и меню в общем пакете.

## Rust и память

Работа над переносом отложена по решению владельца. Старый эксперимент измерял скорость двух функций. Для будущей оценки памяти подготовлена методика с одинаковыми idle/project/docs сценариями и раздельными измерениями Electron, extension host и языковых серверов. Сумма RSS включает общие страницы и на macOS зависит от компрессии. [Документация Electron о метриках памяти](https://www.electronjs.org/docs/latest/api/process#processgetprocessmemoryinfo).

Сначала проверить ленивую загрузку, сроки жизни индексов/кэшей и копирование больших данных. Кандидат на небольшой Rust-прототип — только подтверждённая тяжёлая операция, например будущий локальный индекс, а не UI или короткая строковая функция. Сравнивать одинаковые данные и жизненный цикл с TypeScript, учитывая память процесса/моста, копии, Unicode, отмену и возврат ресурсов. Worker сам по себе не доказывает меньшую RAM.

Отдельный эксперимент в Node показал, что при импорте примерно 64 МиБ синтетических документов последовательная обработка файлов снизила медианный пик памяти со 154 до 122 МиБ. Результат относится к тестовому процессу, проверка внутри IDE ещё предстоит. [Протокол и результаты замеров](agent-reports/development-wave-1.md#первый-замер-импорта-документации).

Решение о переносе требует измеримого выигрыша в общем сценарии, отсутствия функциональных регрессий и отдельной проверки поставки native-компонента. При отсутствии выигрыша сохранять действующую реализацию; экспериментальные инструменты и ненужный бинарный код в продукт не возвращать. Архитектор отвечает за границу, QA — за воспроизводимые измерения, безопасник — за IPC/файлы/права, тимлид — за решение и интеграцию.

## Общая приёмка пакета

Целевые проверки выполняются в task-checkout, независимое ревью — до интеграции. Затем один общий цикл typecheck/интеграция → production package → native smoke с реальным Workspace Trust и проверкой отсутствия фоновой сети → подпись/privacy/ASAR → релиз. Документационный план и отдельная завершённая задача не являются причиной пересборки. До этого новые функции не объявляются установленными владельцу.
